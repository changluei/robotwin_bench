# Head 方向估计的数据链复核

用户质疑“展示给 head 后安装方向是否直接使用 GT”。本次只检查已保存的 `final400_S` 源码、图像和日志，并离线复算；没有启动模拟器或继续候选搜索，也没有修改原结果。

**该运行的安装朝向来自 head RGB-D 的四色标记配准，没有把实例的隐藏底键 GT 直接作为安装方向输入。** 离线复算只读取 `result.json` 所列的文件，不读取 `*_gt.json/jsonl`，不创建场景或物体。

实际链路：

1. 场景给实体底键和颜色点共同施加隐藏的 `T_module_key`；这个变换只留在场景生成和评估侧。
2. 检测器预先知道四种颜色对应的点在**键局部坐标系**中的位置、相机标定，以及 RGB-D 深度。局部模板对全部实例相同，没有给出当前键相对模块/夹爪的朝向。
3. 从 head RGB 的颜色连通域取得像素中心，用深度和内参反投影为相机中的三维点，SVD 刚体配准得到键的位置与方向，再经相机标定和机器人 FK 得到 `T_ee_key`。
4. 控制器只在有效观测后使用 `T_world_socket @ inverse(T_ee_key)` 生成末端目标。固定定位座的坐标/方向是预先给定的公开夹具标定；并未声称定位座也是本轮视觉估计出来的。

日志证据：2.4 s 无完整标记；2.5 s 每色 5 个像素，等待一致性；2.6 s 每色 13/12/12/11 像素，通过一致性，此时首次生成安装目标。展示动作是开发阶段搜索后保存的预设动作，安装方向则等待图像估计，并未随该动作写成固定答案。

离线复核结果见 [result.json](/home/inspur/project/RoboTwin/experiments/held_module_key/head_dataflow_audit/result.json)：

- 从保存的真实 head RGB-D 重算位姿，和原位姿日志矩阵最大差 6.24×10⁻⁸；重新计算安装目标，和原控制命令最大差 6.46×10⁻⁸。
- 离线把 RGB 清零或把深度清零，检测器均无法输出键位姿。这只是输入消融，没有修改实际策略相机接口或用作 H/S 成绩。
- 离线交换红/蓝、绿/黄的颜色对应关系，计算的安装朝向改变 180°。这表明朝向依赖图像标记；同时也暴露出本实现**没有独立使用真实键轮廓核对标记答案**。
- 本次只保存并复算了 2.6 s 的原始 RGB-D 单帧。2.5/2.6 s 的两帧接受关系来自原日志，不能把单帧复算说成完整两帧重放。

**必须保留的感知简化：** 这是已知人工标记模板辅助的、使用模拟器理想深度的位姿估计。它没有实现无标记键形状识别，没有独立的实体键几何方向复核，也没有证明在真实深度噪声、标记误检和模糊条件下仍然可靠。机械入座约束由真实键/孔碰撞决定，但感知几乎完全依赖标记；如果“标记仅作辅助”要求独立几何识别，那么这一部分尚未完成。此前视频没有充分说明这种简化，应结合本复核理解，不能将它当作成熟的真实场景视觉安装能力。
